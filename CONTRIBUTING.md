# Contributing

Tour de Home stays focused on one rider, one FTMS trainer, GPX routes, and local ride records. Discuss major product changes before implementing them.

## Get running

Use Node 24.15.0, run `npm ci`, then `npm run dev`. Try **First Ride → Demo Selected Route**. No trainer, account, private files, or environment variables are needed. Use the supported Node version from `.node-version`; CI uses it too.

## Make a change

1. Reproduce the issue, or describe the intended user outcome.
2. Keep changes focused. Preserve existing saved rides and preference keys.
3. Add a regression test when behavior, data integrity, device control, or an input boundary changes.
4. Run `npm test`, `npm run build`, and `npm run release:check`. For ride lifecycle changes, run `npm run test:browser` using Chrome. For asset/hosting changes, follow the subpath browser check in the README.
5. Describe what changed, why, the checks you actually ran, and anything unverified. For UI work include a screenshot; for hardware work identify the trainer, firmware, OS, and browser.

Never claim a mock proves physical resistance behavior. Never weaken a safety or persistence check just to obtain a passing build.

## Routes and art

Submit only material you can redistribute. Include its origin, license, attribution, and how it was created. Do not add race-course downloads, personal rides, screenshots from games, or private reference images without documented redistribution rights. Synthetic sample routes are generated by `npm run samples:generate`.

Every file under `public/` is inventoried with a SHA-256 checksum in `docs/asset-inventory.json`. Update the entry only after reviewing its provenance. Generated art should record its prompt, whether a reference was used, and any source rights. Runtime dependency changes require `npm run licenses:generate`, review of `docs/dependency-licenses.json`, and updating the notices-file checksum.

## Dependency and workflow changes

Keep the lockfile. Inspect upstream licenses, advisories, and browser compatibility before replacing a dependency. Use isolated environments for untrusted contributions; dependency installation can execute package scripts. CI has read-only repository permissions and no deployment secrets. Do not add privileged pull-request workflows.

## Communication and licensing

Be constructive, specific, and respectful. Report security issues using SECURITY.md rather than a public issue containing exploit data or secrets. Contributions are offered under this project's MIT license; third-party material must retain its own required notices. Do not commit credentials, local logs, or generated browser profiles.
